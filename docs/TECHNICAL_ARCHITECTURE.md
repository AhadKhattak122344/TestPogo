# Technical Architecture Document for Bare-Metal ARM Cloud Environments

## 1. Executive Summary

This document specifies the architecture, requirements, and implementation plan for a bare-metal ARM64 server environment capable of hosting virtualized Android instances that satisfy Google Play Integrity hardware-backed attestation. The design targets Ampere Altra and equivalent ARM64 server hardware, uses KVM with TrustZone pass-through, and produces Android guests that present as coherent, attested devices at the attestation layer.

The design is application-agnostic. It describes general infrastructure for scenarios requiring authenticated Android guests on ARM64 cloud hardware.

## 2. Technical Analysis: Hardware Attestation Mechanisms

### 2.1 The Attestation Chain

Google Play Integrity relies on a hardware-anchored certificate chain. Understanding the chain is prerequisite to designing infrastructure that satisfies it.

```
┌──────────────────────────────────────────────────────────────┐
│                    ATTESTATION ROOT OF TRUST                 │
│                                                              │
│  Google Root CA (hardcoded in Play Services)                 │
│       │ signs                                                │
│       ▼                                                      │
│  Google Hardware Attestation Intermediate CA                 │
│       │ signs                                                │
│       ▼                                                      │
│  Device OEM Intermediate CA                                  │
│       │ signs                                                │
│       ▼                                                      │
│  Per-Device Attestation Key (burned into TEE at manufacture) │
│       │ signs                                                │
│       ▼                                                      │
│  Attestation Certificate (generated per attestation request) │
│       │                                                      │
│       ▼                                                      │
│  Play Integrity Verdict                                      │
└──────────────────────────────────────────────────────────────┘
```

The critical property: the per-device attestation key lives inside the Trusted Execution Environment (TEE). It is generated by the OEM during manufacturing, provisioned into a hardware-protected keystore, and never leaves the TEE in plaintext. The key cannot be extracted by software.

### 2.2 Trusted Execution Environment Options on ARM

| TEE Implementation | Owner | Availability | Notes |
|---|---|---|---|
| ARM TrustZone (secure world) | ARM | All ARM cores | Hardware partition between normal and secure world |
| Google Titan M / M2 | Google | Pixel devices | Dedicated security chip, TEE+SE |
| Qualcomm SPU / QSEE | Qualcomm | Snapdragon SoCs | Vendor TEE |
| Samsung Knox Vault | Samsung | Galaxy devices | Isolated security processor |
| Ampere Altra + TF-A + OP-TEE | Open source | Ampere servers | Available but not Google-certified |
| AWS Nitro TPM / Nitro Enclaves | AWS | EC2 instances | Not usable for Android attestation |

The distinction that matters: Google's attestation chain only trusts keys that were provisioned into a TEE by a Google-approved OEM during manufacturing. An Ampere Altra server running OP-TEE has a TEE, but its keys are not in Google's trust database, so attestations signed by it are rejected.

### 2.3 Why Standard ARM VPS Fails

| Failure Mode | Cause |
|---|---|
| No TEE at all | Many ARM VPS run in containers or lightweight VMs without TrustZone exposure |
| TEE present but no OEM key | QEMU/KVM exposes a generic TEE with no Google-attested device key |
| Kernel does not expose TEE | Guest kernel lacks the OP-TEE driver or the device tree does not pass through the secure memory region |
| Attestation key not provisioned | Even if TEE is reachable, no per-device key exists |
| Build fingerprint mismatch | Guest build.prop reports a model that does not match the TEE's identity |

### 2.4 What Makes Cloud Phone Providers Succeed

Cloud phone providers succeed because they do not virtualize Android in the same way a general-purpose cloud does. They either:

- Run Android on real ARM phones in a data center
- Use ARM server SoCs with vendor-provisioned TEE keys and Google partnerships
- Satisfy attestation at the OEM level by running on certified hardware

They are not bypassing attestation. They are satisfying it with hardware that carries a Google-trusted key.

### 2.5 The Keybox Dependency

The alternative to a genuine Google-trusted TEE is a keybox.xml — a certificate chain containing a real OEM device's private key. This is a file, not hardware. It is injected into the attestation response by a runtime module.

| Property | Genuine TEE | Keybox Injection |
|---|---|---|
| Attestation source | Hardware | Software (runtime module) |
| Requires ARM | No | No |
| Revocable by Google | Per-device | Per-keybox (all users) |
| Scale limit | Hardware available | Keybox supply |
| Long-term viability | Sustainable | Fragile |

This document focuses on the genuine TEE path, which is the only sustainable architecture for a fleet. Keybox injection is noted as a fallback where hardware attestation is not available.

## 3. Architecture Design for ARM64 Android Virtualization

### 3.1 Reference Hardware

| Component | Specification | Notes |
|---|---|---|
| CPU | Ampere Altra / Altra Max (80-128 cores) | No SMT, consistent per-core performance |
| RAM | 256-512 GB DDR4 ECC | 8-16 GB per Android instance |
| Storage | NVMe SSD, 4-8 TB | Fast random IO for Android system images |
| Network | 25-100 GbE | Required for fleet-scale ADB and inter-VM |
| Firmware | UEFI + TF-A + OP-TEE | TrustZone exposed to hypervisor |
| GPU (optional) | Ampere Altra has no GPU; add PCIe GPU | Required for accelerated graphics |

Ampere Altra lacks a GPU. GPU acceleration is achieved via:

- PCIe passthrough of an AMD/NVIDIA GPU to individual guests (limits scale)
- VirGL over VirtIO-GPU (software rendering, moderate performance)
- Cloud-based rendering offload (complex)

### 3.2 TrustZone / TEE Pass-Through to KVM

TrustZone is exposed to the hypervisor through ARM's EL3 firmware (TF-A) and a secure partition manager. The hypervisor then exposes TEE to guests via OP-TEE virtualization using the ARM SMMU.

```
┌───────────────────────────────────────────────────┐
│              ARM64 SERVER (Ampere Altra)            │
│                                                     │
│  ┌─────────────────────────────────────────────┐  │
│  │  EL3: ARM Trusted Firmware (TF-A)           │  │
│  │  - Secure Monitor                           │  │
│  │  - SPMC (Secure Partition Manager Core)     │  │
│  └─────────────────────────────────────────────┘  │
│                          │                          │
│  ┌─────────────────────────────────────────────┐  │
│  │  Secure World (TrustZone)                    │  │
│  │  - OP-TEE OS                                 │  │
│  │  - Hardware-backed keystore                  │  │
│  │  - Attestation key storage (if provisioned)  │  │
│  └─────────────────────────────────────────────┘  │
│                          │                          │
│  ┌─────────────────────────────────────────────┐  │
│  │  Normal World                                │  │
│  │  ┌───────────────────────────────────────┐  │  │
│  │  │  Linux Host + KVM                      │  │  │
│  │  │  - OP-TEE virtualization (tee-supplicant) │  │  │
│  │  │  - vSMMU for secure memory isolation   │  │  │
│  │  └───────────────────────────────────────┘  │  │
│  │                          │                     │  │
│  │  ┌───────────────────────────────────────┐  │  │
│  │  │  Android Guest (VM)                    │  │  │
│  │  │  - OP-TEE client driver               │  │  │
│  │  │  - Keymaster HAL                       │  │  │
│  │  │  - Gatekeeper HAL                      │  │  │
│  │  └───────────────────────────────────────┘  │  │
│  └─────────────────────────────────────────────┘  │
└───────────────────────────────────────────────────┘
```

Critical constraint: The TEE on an Ampere server is not a Google-certified attestation root. It can service general keystore operations, but it cannot produce a Google-accepted attestation certificate unless the server's OEM has provisioned a Google-attested key. Ampere servers, in general, do not have this key.

### 3.3 GPU Acceleration Options

| Option | Performance | Scalability | Notes |
|---|---|---|---|
| VirGL over VirtIO-GPU | 30-40% of native | High | Shared GPU across guests |
| GPU passthrough | Native | 1 guest per GPU | Requires dedicated GPU per VM |
| vfio-mdev (SR-IOV) | Near-native | 4-8 guests per GPU | Requires SR-IOV-capable GPU |
| Cloud rendering | Variable | High | Offload rendering, high latency |

For a fleet, VirGL is the only practical default.

### 3.4 Kernel-Level Patches

The Android guest kernel must:

- Recognize the OP-TEE device (/dev/tee0, /dev/teepriv0)
- Route Keymaster/Gatekeeper calls to the TEE
- Report a build fingerprint consistent with the TEE's reported model
- Satisfy the Play Integrity API checks

Because the Ampere TEE is not Google-attested, the software stack must supply a keybox.xml to the attestation module to make attestation responses signed by a Google-trusted key. In practice this means:

| Layer | Purpose |
|---|---|
| OP-TEE driver in guest | Provides a TEE interface to Android |
| Keymaster HAL | Routes keystore operations to TEE |
| Attestation module | Intercepts attestation, substitutes keybox |
| Build-property module | Aligns build properties for Play Integrity |

This is a hybrid: hardware TEE for general keystore, software keybox for Google attestation.

## 4. Identity and Configuration Consistency

### 4.1 Identity Components

Every Android instance must present a coherent identity across all layers.

| Layer | Component | Source |
|---|---|---|
| Kernel | uname -a, /proc/cpuinfo, /proc/version | Kernel patches |
| System | ro.build.fingerprint, ro.product.model | build.prop modification |
| Hardware | Sensor list, GPU renderer, CPU features | Sensor HAL, GPU driver |
| Network | Public IP geolocation, DNS | VPN/proxy routing |
| Software | Installed apps, telephony, SIM state | Framework patches |
| Attestation | Keybox signature | Attestation module |
| Behavioral | Movement, timing, session patterns | Application layer |

All must be consistent. A single mismatch between the attested device model and the reported build fingerprint triggers a flag.

### 4.2 Device Identity Generation

Each instance requires a unique identity from a pool of validated profiles.

```python
class DeviceIdentity:
    """Represents a single Android device identity."""
    
    def __init__(self, profile_id: str, keybox: bytes):
        self.profile_id = profile_id           # e.g., "pixel4-flame-01"
        self.keybox = keybox                   # Matched keybox for this profile
        self.android_id = secrets.token_hex(8)
        self.imei = self._generate_imei()
        self.mac = self._generate_mac()
        self.serial = secrets.token_hex(8).upper()
    
    def _generate_imei(self) -> str:
        # Luhn-valid 15-digit IMEI
        tac = "35123456"        # TAC prefix for a real device model
        serial = f"{secrets.randbelow(10**6):06d}"
        partial = tac + serial
        check = self._luhn_check(partial)
        return partial + str(check)
    
    def _luhn_check(self, number: str) -> int:
        digits = [int(d) for d in number]
        for i in range(len(digits) - 1, -1, -2):
            digits[i] *= 2
            if digits[i] > 9:
                digits[i] -= 9
        return (10 - (sum(digits) % 10)) % 10
    
    def _generate_mac(self) -> str:
        prefix = "00:16:3E"
        suffix = ":".join(f"{secrets.randbelow(256):02x}" for _ in range(3))
        return f"{prefix}:{suffix}"
```

### 4.3 Coherence Verification

Before an instance is marked ready, all identity layers must agree:

```python
async def verify_identity_coherence(instance) -> bool:
    """Check that all identity layers agree."""
    
    checks = {}
    
    # Kernel reports the expected model
    uname = await adb_shell(instance, "uname -a")
    checks["kernel"] = "flame" in uname.lower() or "generic" in uname.lower()
    
    # Build properties match the profile
    fp = await adb_shell(instance, "getprop ro.build.fingerprint")
    checks["fingerprint"] = fp == instance.identity.expected_fingerprint
    
    # Attestation passes
    integrity = await adb_shell(
        instance,
        "am broadcast -a com.google.android.gms.INTEGRITY_CHECK"
    )
    checks["integrity"] = "MEETS_DEVICE_INTEGRITY" in integrity
    
    # Network IP geolocation matches reported locale
    ip_geo = await lookup_geo(instance.public_ip)
    checks["network"] = ip_geo.country == instance.identity.country
    
    return all(checks.values())
```

### 6.6 Identity Application Script

```bash
#!/bin/bash
# apply_identity.sh <vm_name> <profile>
# Applies device identity to a running Android guest

set -e

VM_NAME=$1
PROFILE=$2
ADB_TARGET="android-guest-${VM_NAME}"

# Load profile
PROFILE_JSON=$(jq -r ".profiles[\"${PROFILE}\"]" /etc/android-fleet/profiles.json)

MODEL=$(echo "$PROFILE_JSON" | jq -r .model)
MANUFACTURER=$(echo "$PROFILE_JSON" | jq -r .manufacturer)
FINGERPRINT=$(echo "$PROFILE_JSON" | jq -r .fingerprint)
BUILD_DESC=$(echo "$PROFILE_JSON" | jq -r .build_description)
ANDROID_ID=$(openssl rand -hex 8)
SERIAL=$(openssl rand -hex 8 | tr 'a-z' 'A-Z')

# Apply build properties
adb -s "$ADB_TARGET" shell su -c "
    setprop ro.product.model '${MODEL}'
    setprop ro.product.manufacturer '${MANUFACTURER}'
    setprop ro.build.fingerprint '${FINGERPRINT}'
    setprop ro.build.description '${BUILD_DESC}'
    setprop ro.serialno '${SERIAL}'
"

# Persist to build.prop
adb -s "$ADB_TARGET" shell su -c "
    mount -o rw,remount /system
    sed -i '/^ro.product.model=/d' /system/build.prop
    sed -i '/^ro.build.fingerprint=/d' /system/build.prop
    echo 'ro.product.model=${MODEL}' >> /system/build.prop
    echo 'ro.product.manufacturer=${MANUFACTURER}' >> /system/build.prop
    echo 'ro.build.fingerprint=${FINGERPRINT}' >> /system/build.prop
    mount -o ro,remount /system
"

# Apply identity config for Android framework
cat > /tmp/identity.json <<EOF
{
    "android_id": "${ANDROID_ID}",
    "serial": "${SERIAL}",
    "model": "${MODEL}",
    "manufacturer": "${MANUFACTURER}"
}
EOF
adb -s "$ADB_TARGET" push /tmp/identity.json /data/local/tmp/identity.json
adb -s "$ADB_TARGET" shell su -c "
    cp /data/local/tmp/identity.json /data/system/device_identity.json
    chmod 644 /data/system/device_identity.json
"

# Clear Google Services to force re-registration
adb -s "$ADB_TARGET" shell pm clear com.google.android.gms
adb -s "$ADB_TARGET" shell pm clear com.google.android.gsf
adb -s "$ADB_TARGET" shell pm clear com.android.vending

# Reboot to apply
adb -s "$ADB_TARGET" reboot

echo "[OK] Identity applied to ${VM_NAME}"
```

### 6.7 Keybox Rotation Service

```python
# keybox_manager.py
import asyncio
import aiohttp
from datetime import datetime, timedelta
from dataclasses import dataclass
from typing import Dict, List, Optional

@dataclass
class Keybox:
    keybox_id: str
    content: bytes
    profile: str           # "pixel4", "pixel5", etc.
    issued_at: datetime
    revoked: bool = False
    uses: int = 0

class KeyboxManager:
    MAX_USES_PER_KEYBOX = 50           # Conservative limit before rotation
    REVOCATION_CHECK_INTERVAL = 3600   # 1 hour
    
    def __init__(self, pool_url: str, adb_controller):
        self.pool_url = pool_url
        self.adb = adb_controller
        self.pool: Dict[str, Keybox] = {}
        self.assignments: Dict[str, str] = {}  # instance_id -> keybox_id
    
    async def fetch_pool(self) -> List[Keybox]:
        """Fetch fresh keyboxes from community pool."""
        async with aiohttp.ClientSession() as session:
            async with session.get(self.pool_url) as resp:
                data = await resp.json()
                return [
                    Keybox(
                        keybox_id=k["id"],
                        content=k["content"].encode(),
                        profile=k["profile"],
                        issued_at=datetime.fromisoformat(k["issued_at"]),
                    )
                    for k in data["keyboxes"]
                ]
    
    def assign(self, instance_id: str, profile: str) -> Optional[Keybox]:
        """Assign an unused keybox to an instance."""
        candidates = [
            kb for kb in self.pool.values()
            if kb.profile == profile
            and not kb.revoked
            and kb.uses < self.MAX_USES_PER_KEYBOX
            and kb.keybox_id not in self.assignments.values()
        ]
        if not candidates:
            return None
        
        candidates.sort(key=lambda kb: kb.issued_at, reverse=True)
        chosen = candidates[0]
        
        self.assignments[instance_id] = chosen.keybox_id
        return chosen
    
    async def verify_assignment(self, instance_id: str) -> bool:
        """Check that the instance still passes attestation."""
        result = await self.adb.shell(
            instance_id,
            "am broadcast -a com.google.android.gms.INTEGRITY_CHECK"
        )
        return "MEETS_DEVICE_INTEGRITY" in result
    
    async def rotate(self, instance_id: str, profile: str) -> bool:
        """Rotate the keybox assigned to an instance."""
        old_keybox_id = self.assignments.get(instance_id)
        if old_keybox_id:
            self.pool[old_keybox_id].uses += 1
        
        new_keybox = self.assign(instance_id, profile)
        if not new_keybox:
            return False
        
        await self.adb.push_file(
            instance_id,
            new_keybox.content,
            "/data/adb/attestation_module/keybox.xml"
        )
        
        await self.adb.shell(
            instance_id,
            "su -c 'am force-stop com.google.android.gms'"
        )
        
        return await self.verify_assignment(instance_id)
    
    async def start_rotation_loop(self):
        """Periodically verify and rotate assignments."""
        while True:
            for instance_id, keybox_id in list(self.assignments.items()):
                healthy = await self.verify_assignment(instance_id)
                if not healthy:
                    profile = self.pool[keybox_id].profile
                    await self.rotate(instance_id, profile)
            
            await asyncio.sleep(self.REVOCATION_CHECK_INTERVAL)
```

### 7.2 Instance Lifecycle API

```python
# orchestrator.py
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
import libvirt
from typing import Optional

app = FastAPI()
conn = libvirt.open("qemu:///system")

class InstanceRequest(BaseModel):
    name: str
    profile: str = "pixel4"
    cpu_cores: int = 4
    ram_gb: int = 8

@app.post("/instances")
async def create_instance(req: InstanceRequest):
    # 1. Clone template
    vm = await clone_template(req.name, req.cpu_cores, req.ram_gb)
    
    # 2. Generate identity
    identity = DeviceIdentity(profile_id=req.profile)
    
    # 3. Assign keybox
    keybox = keybox_manager.assign(vm.name(), req.profile)
    if not keybox:
        raise HTTPException(503, "No keybox available for this profile")
    
    # 4. Start VM
    vm.create()
    
    # 5. Wait for ADB
    await wait_for_adb(vm.name(), timeout=180)
    
    # 6. Apply identity
    await apply_identity(vm.name(), identity, keybox)
    
    # 7. Verify attestation
    if not await verify_attestation(vm.name()):
        await vm.destroy()
        raise HTTPException(500, "Attestation failed after provisioning")
    
    return {
        "name": vm.name(),
        "state": "running",
        "profile": req.profile,
        "keybox_id": keybox.keybox_id,
    }

@app.delete("/instances/{name}")
async def destroy_instance(name: str):
    vm = conn.lookupByName(name)
    if vm.isActive():
        vm.destroy()
    vm.undefine()
    keybox_manager.release(name)
    return {"name": name, "state": "destroyed"}
```

## 8. Operational Constraints and Limits

### 8.1 The Keybox Dependency

Without a keybox, this entire stack does not pass Google attestation, because Ampere's TEE is not Google-certified. The hardware provides a real TEE for general keystore use, but the Google attestation chain does not trust it.

This means the architecture has two layers:

| Layer | Source | Purpose |
|---|---|---|
| Hardware TEE | Ampere + OP-TEE | General keystore, encryption, secure operations |
| Software keybox | Community pool | Google attestation |

If the keybox pool dries up, the fleet fails.

### 8.2 Scaling the Keybox Pool

| Fleet Size | Keybox Rotation Burden |
|---|---|
| 1-5 instances | 1-2 keyboxes, weekly rotation |
| 5-25 instances | 5-25 keyboxes, daily rotation |
| 25-100 instances | 25-100 keyboxes, 12-hour rotation |
| 100+ instances | Not feasible with community keyboxes |

For 100+ instances, the only viable path is hardware with a real Google-attested TEE, which Ampere does not provide. Realistically, that means:

- Physical Android devices on a device farm
- Cloud phone providers with Google partnership
- Custom hardware with a Google-provisioned TEE (not commercially available)

### 8.3 Detection Beyond Attestation

Attestation is only one layer. The target application also:

- Reads hardware sensors (accelerometer, gyroscope, barometer)
- Checks GPU renderer strings
- Analyzes touch timing and gesture patterns
- Correlates network metadata with GPS
- Monitors session patterns

Each of these must be addressed independently.

| Behavioral detection is not solved by attestation | Application-layer work still required |

### 9.3 Final Assessment

An ARM64 bare-metal fleet on Ampere can:

- Run Android guests natively (no translation)
- Provide a hardware TEE for general cryptographic operations
- Pass Google attestation if supplied with valid keyboxes
- Scale to ~50 instances with active keybox rotation

An ARM64 bare-metal fleet on Ampere cannot:

- Provide a Google-attested TEE natively
- Scale beyond community keybox availability
- Avoid application-layer behavioral detection
- Match the reliability of a physical device farm or a certified cloud phone provider

For a production fleet, the practical options remain: cloud phone providers with Google attestation, or physical devices. The ARM64 server path is viable for research and moderate-scale operation, but its attestation layer is a hard external dependency.
